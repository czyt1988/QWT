# Qt 主流绘图控件的渲染性能：Qwt、QCustomPlot、Qt Charts、QIm 四方实测

> **摘要** —— "哪个 Qt 绘图库最快"通常用一次扫描来回答：横轴点数、纵轴帧时间，画两三条线，宣布胜者。这种测量只回答了**一种**配置，并把四个彼此独立的成本中心悄悄合成一个数字。本文沿八个维度实测 Qt 开发者真正会在这四者之间选择的库——**Qwt 7.5、QCustomPlot 2.1.0、Qt Charts 6.7、QIm 0.0.3（ImPlot）**：点数、曲线数、画布尺寸、数据交接与重绘的拆分、内置降采样的代价*与*逐像素保真度、帧时间分布、每采样内存、启动开销，并对其中两个同时提供栅格与 OpenGL 后端的库做了后端对比。所有测量由同一套基准程序（`examples/bench/chartbench`）驱动，每个库独占一个进程、走完全相同的协议。协议本身也是结论的一部分：`QOpenGLWidget` 会把普通 `repaint()` 推迟到 Qt 的合成阶段，因此"朴素"的计时方式会把一条 10 万点曲线报成 **0.004 ms**；本文给出同步驱动 GL 入口的做法，并如实记录那个无法用该方式测量的库。17 张图与 15 张表把四个库所处的三种工况分开，并说明**选降采样策略比选库、选后端、选画布都值钱两个数量级**。

> **摘要 — 核心结论**
>
> - **排名在 1 000 点到 5 000 000 点之间反转两次。**1 000 点时 Qt Charts 一帧 0.528 ms，Qwt 是 2.025 ms（3.8 倍）；5 000 000 点时 Qwt 需要 515.6 ms，而 QCustomPlot 要 985.5 ms（1.9 倍）、Qt Charts 要 779.0 ms（1.5 倍）。四个库在 100 000 点时都还在 60 Hz 预算之内，到 250 000 点时全部超预算，每采样的边际成本在库与库之间最多相差 2.8 倍。
> - **降采样是唯一带有两个数量级的杠杆。**100 万点时 QIm 的 `Auto`（MinMaxLTTB）一帧只要 **1.277 ms**——比它自己不降采样快 62 倍，比完全没有降采样可用的 Qt Charts（161.8 ms）快 **127 倍**。Qwt 的 `FilterPointsMinMaxLTTB` 达到 5.200 ms（自身基线 19.8 倍），QCustomPlot 的自适应采样 6.163 ms（30.9 倍）。
> - **保真度把算法分成两族，而最快的并不是最糊的。**Qwt 的 MinMaxLTTB 改动 5.56% 像素、着墨比 0.821；`FilterPointsAggressive` 只保留 0.394 的曲线着墨，QCustomPlot 自适应采样保留 0.915。而 Qwt 那个经典的 `FilterPoints` 过滤器与"完全不降采样"**逐像素完全相同**（改动 0.00%），同时还更慢一点。
> - **数据 API 比渲染器更贵。**10 万点窗口下，四个库画图花 8.1–14.6 ms（相差 1.8 倍），但交接数据花 **230 µs 到 141.7 ms**（相差 616 倍）。一个独立探针指出 Qt Charts 的钱花在哪里：0.73 ms 用于构造它的 API 要求的 `QList<QPointF>`，48.65 ms 花在 `QXYSeries::replace()` 内部，25.55 ms 花在两次 `QValueAxis::setRange()`；而同一个 `replace()` 在图表不在活动视图里时只要 1.88 ms，便宜 26 倍。
> - **OpenGL 不是折线图的性能策略，而且两个 GL 实现的回本点差一个数量级。**Qwt 的 GL 画布在 1 000 点时快 1.22 倍，到 500 万点时反而慢 1.50 倍；QCustomPlot 的 GL 绘制缓冲在 1 000 点时每帧要多付 16.1 ms，却在 10 万到 25 万点之间反超自身的栅格路径，500 万点时领先 1.66 倍。
> - **数据量占主导后，每采样内存在库间相差 20 倍以上**：100 万点时 QCustomPlot 16.6 B/采样、Qwt 20.9 B，而 Qt Charts 337.8 B、QIm 427.9 B。同样 100 万点拆成 100 条曲线时，Qt Charts 需要 272.9 MB，QCustomPlot 只要 21.4 MB。
> - **帧时间稳定性是独立于速度的另一根轴。**QIm 在中位数上最好（10 万点静态数据 7.77 ms），相对尾部却最差（p99/p50 = 2.2×，max/p50 = 2.4×）；Qwt 中位数慢 5%（8.14 ms），但离散度最小（到自己最差一帧只有 1.27 倍）。
> - **一项阴性结果如实记录**：在同步帧协议下，Qt Charts 的 `setUseOpenGL(true)` 序列**从未进入帧缓冲**——实测曲线着墨覆盖率 0.0009，而栅格路径是 0.0586——因此该后端被排除，而不是估算一个数字。

## 1. 引言

### 1.1 问题，以及它为何通常被答错

"哪个 Qt 绘图库最快"是 Qt 应用开发里最常被问的问题之一，而能找到的答案几乎都是一次扫描：横轴*点数*、纵轴*帧时间*，两三个库各画一条线，宣布胜者。这种测量只回答了一种配置——一条曲线、一种画布尺寸、静态数据、以及各库降采样默认值的偶然组合——并且把四个彼此独立的成本中心合成一个数字。

由此得出的建议经不起真实应用的检验。一个每秒往滑动窗口追加 10 000 个采样的遥测面板，与一个一次打开五百万点文件再让用户缩放的科研图，成本结构完全不同。50 条各 2 000 点的曲线并不等于"把一条 10 万点的曲线按比例缩小"：每曲线开销与每采样开销长在不同的地方。而最关键的一个设计决策——库在光栅化之前是否削减点集——通常被留在默认值上，于是这种对比测的是默认值，不是库。

本文实测 Qt 开发者真正会在这四者之间选择的库——**Qwt 7.5**、**QCustomPlot 2.1.0**、**Qt Charts 6.7**、**QIm 0.0.3（ImPlot）**——沿八个相互独立的维度，由同一套基准程序以完全相同的协议驱动。

### 1.2 成本模型

一条折线图显示一帧的耗时可拆成

$$
T_{\text{frame}} \;=\; T_{\text{handover}} \;+\; T_{\text{transform}}(N,K)
\;+\; T_{\text{raster}}(N,K,W\!\times\!H) \;+\; T_{\text{compose}}(W\!\times\!H)
\;+\; T_{\text{present}}
$$

其中 $N$ 为每条曲线的采样数，$K$ 为曲线条数，$W\!\times\!H$ 为画布尺寸。这五项各有其归属：

| 项 | 含义 | 谁付这笔账 |
|------|-----------|-------------|
| $T_{\text{handover}}$ | 把新数据拷贝/校验进库自己的容器 | 库的数据 API |
| $T_{\text{transform}}$ | 坐标映射、降采样、裁剪、路径构建 | 库的曲线类 |
| $T_{\text{raster}}$ | 把折线变成像素 | Qt 栅格绘制引擎，或 GPU |
| $T_{\text{compose}}$ | 把渲染结果 blit/合成上屏 | Qt 控件合成，或 GL 控件路径 |
| $T_{\text{present}}$ | 把表面交给窗口系统 | DWM / 平台合成器 |

四个库对这些工作的分配方式差别极大，而且这些差别不是可以互相抵消的常数——它们随**不同的变量**缩放。后文将逐项测量每一个能被隔离出来的项。

### 1.3 本文的贡献

1. **一套让四个库可比的协议**（第 3 节）。难点不在于给一次调用计时，而在于为"一帧"给出一个对 `QPainter` 绘制的 `QWidget` 与对 `repaint()` 被 Qt 推迟到合成阶段的 `QOpenGLWidget` 都成立的定义。3.2 节展示朴素的 `repaint()` 协议会让某个 GL 库看起来快 250 倍，以及基准程序如何避开这一点。
2. **八个测量维度**（第 4 节）：点数、曲线数、画布尺寸、数据交接与重绘、内置降采样、帧时间分布、进程内存、启动开销，外加对同时提供两种后端的两个库做栅格/OpenGL 对比。
3. **降采样的逐像素保真度指标**（4.5 节），把每个库与*它自己*的全分辨率渲染对比——这正是让保真度数字能在版式各异的库之间可比的原因。
4. **可复现的基准程序**（`examples/bench/chartbench`，8 个测试套件、6 个进程）与完整的分析管线（`docs/assets/bench/`），能重新生成本文的每一张图与每一个数字。
5. **如实记录阴性结果**（第 6 节）：Qt Charts 的 OpenGL 序列路径无法用同步帧协议测量，本文给出像素证据，而不是一个看起来合理的数字。

## 2. 四个库，四条渲染管线

实测差异并非偶然，每个库的数字都能从"它的架构把工作放在哪里"推导出来。本节从源码里读出四条管线，因为这些结构事实正是后文测量要证实或推翻的对象。

```mermaid
flowchart TB
    subgraph Qwt["Qwt 7.5"]
        A1["QwtPointMapper::toPolygonF<br/>映射 + 可选降采样"] --> A2["QwtClipper<br/>裁剪"] --> A3["QPainter::drawPolyline<br/>CPU 栅格引擎"] --> A4["backing store 位图<br/>+ blit"]
    end
    subgraph QCP["QCustomPlot 2.1"]
        B1["getOptimizedLineData<br/>像素列 min/max"] --> B2["QCPPainter::drawPolyline"] --> B3["绘制缓冲<br/>QPixmap 或 FBO"] --> B4["控件重绘<br/>blit"]
    end
    subgraph QTC["Qt Charts 6.7"]
        C1["每条序列一个 QList&lt;QPointF&gt;"] --> C2["每条序列一个 QPainterPath"] --> C3["QGraphicsScene 渲染<br/>CPU 栅格引擎"] --> C4["QGraphicsView 视口"]
    end
    subgraph QIM["QIm 0.0.3"]
        D1["ImPlot Getter<br/>+ 可选降采样"] --> D2["ImDrawList<br/>每段 4 个顶点"] --> D3["ImGui::Render<br/>一次 draw call"] --> D4["GPU 光栅化<br/>画进控件 FBO"]
```

四个盒子的区别在于：*逐采样循环跑在哪里*（Qwt/QIm 是向量化变换或逐段展开，Qt Charts 是逐 `QPointF` 对象），*谁来光栅化*（三个用 CPU，QIm 用 GPU），以及*帧与帧之间缓存了什么*（在整帧重绘下四者都不缓存）。

### 2.1 Qwt：一个映射器、一条折线、一个 backing store

`QwtPlotCurve::drawLines()`（`src/plot/qwt_plot_curve.cpp`）把整条逐采样管线放在一处：`QwtPointMapper::toPolygonF()` 把数据映射到屏幕坐标**并**施加所配置的降采样，`QwtClipper::clipPolygonF()` 相对画布裁剪，`QwtPainter::drawPolyline()` 把结果交给 `QPainter`。这里没有逐采样对象，也没有中间的 `QGraphicsItem`：$N$ 个采样的代价就是一次线性扫描，产出一个 `QPolygonF`。

降采样这一步值得精确陈述，因为它解释了 4.5 节的结果。`QwtPlotCurve::PaintAttribute` 提供五种策略，它们的输出预算都以*像素列*计（$W$ = 画布宽度）：

| 属性 | 规则 | 输出预算 |
|-----------|------|---------------|
| `FilterPoints` | 丢弃重复点与可视区外的点 | $N$（最坏情况） |
| `FilterPointsAggressive` | 把映射到同一整数坐标的连续点压缩为 first/min/max/last | $\le 4W$ |
| `FilterPointsPixel` | 按像素列分桶，输出 first/min/max/last 并做亚像素定位 | $\approx 4W$ |
| `FilterPointsLTTB` | Largest-Triangle-Three-Buckets | $\approx 4W$ |
| `FilterPointsMinMaxLTTB` | 每桶取 min/max | $\approx 2W$ |

默认值很重要，而且不太可能是读者猜到的那一个。`QwtPlotCurve` 的构造是

```cpp
paintAttributes(QwtPlotCurve::ClipPolygons | QwtPlotCurve::FilterPointsLTTB)
```

（`src/plot/qwt_plot_curve.cpp:84`）——**Qwt 7.5 默认就开启 LTTB 降采样**，项目的 `CHANGES.md` 记录该默认值自 v7.3.2 起就存在（v7.4.2 之前是 MinMax 桶，v7.5.0 起是保形的真 LTTB）。四个降采样标志各自独立开关（`qwt_plot_curve.cpp:611-619`），因此可以任选其一或全部关掉而不影响其他。本文随后的所有讨论都基于这一条：**所有测量都显式配置过滤器，绝不使用库的默认值**——因为在 Qwt 上画 `setSamples()` 再调 `replot()`，测到的其实是 LTTB 之后的结果。

画布是带 backing store 的 `QFrame`（`QwtPlotCanvas`），而 `replot()` 在重绘前先让该缓存失效，所以整帧重绘永远走"全部重画、再 blit"这条路。`ImmediatePaint` 属性把 `replot()` 变成同步的 `repaint()`，基准程序正是用这个钩子来定义"Qwt 的一帧已完成"。

### 2.2 QCustomPlot：阈值自适应的采样器

QCustomPlot 的 graph 把 `QCPGraphData` 记录——一个 key 加一个 value，x64 上 16 字节（`qcustomplot.h:5427-5444`）——存在有序容器里，`QCPGraph::draw()` 在绘制前调用 `getOptimizedLineData()`（`examples/bench/chartbench/qcustomplot.cpp:21661`）。这个采样器是一个**像素列 min/max 聚类器**，真正有意思的是它的启用条件：

```cpp
int dataCount = int(end-begin);
int maxCount = (std::numeric_limits<int>::max)();
if (mAdaptiveSampling)
{
  double keyPixelSpan = qAbs(keyAxis->coordToPixel(begin->key)-keyAxis->coordToPixel((end-1)->key));
  if (2*keyPixelSpan+2 < static_cast<double>((std::numeric_limits<int>::max)()))
    maxCount = int(2*keyPixelSpan+2);
}
if (mAdaptiveSampling && dataCount >= maxCount) // use adaptive sampling only if there are at least
                                                // two points per pixel on average
```

它的阈值不是采样数，而是**密度**：只有当可见数据平均每个像素列至少有两个点时才开始降采样。这让决策自动跟随画布尺寸与缩放级别，也是 QCustomPlot 的实测交叉点与 Qwt 的"属性开关"落在不同位置的原因。它默认开启；基准程序在原始测量中显式关闭（`setAdaptiveSampling(false)`）。

绘制进入一个*绘制缓冲*，其实现由编译期决定：`QCPPaintBufferPixmap`（一个 `QPixmap` 加一个 `QPainter`），或在定义 `QCUSTOMPLOT_USE_OPENGL` 时用 `QCPPaintBufferGlFbo`（FBO 上的 `QOpenGLPaintDevice`）。`replot(rpImmediateRefresh)` 把所有图层画进该缓冲，然后同步重绘控件——这就是 QCustomPlot 的一整帧。

### 2.3 Qt Charts：场景图，以及"数据即对象"

Qt Charts 不是一个绘图控件，而是一个带图表 item 的 `QGraphicsScene`。`QLineSeries` 用 `QList<QPointF>` 存数据，因此交接 $N$ 个采样就意味着构造 $N$ 个 `QPointF` 对象——API 没有提供裸数组入口。绘制时在场景渲染内部为每条序列构建一个 `QPainterPath`，而 `QChartView` 是一个 `QGraphicsView`，由它的 `paintEvent` 渲染该场景。

这一结构直接导出两个后果，两者都在测量中显现：数据交接相对其他库昂贵（4.4 与 4.8 节），并且**完全没有任何内置降采样**——给多少就画多少。Qt Charts 提供的唯一加速是 `QAbstractSeries::setUseOpenGL(true)`，它改走 GL 绘制设备而非栅格引擎；第 6 节说明这条路径为何无法测量。

### 2.4 QIm：ImPlot 之上的保留模式外壳，逐段四边形

QIm 是把 Dear ImGui/ImPlot 包装进 Qt 的库。它的 figure 控件是一个 `QOpenGLWidget`；`paintGL()` 构建一帧 ImGui（`QtImGui::newFrame` → 节点树 → `ImGui::Render`）并提交。真正有意思的是 ImPlot 怎么画一条线：它不描边路径。它的渲染器遍历数据，在 CPU 上把**每一段线**展开成一个四边形写进 `ImDrawList`：

```cpp
struct RendererLineStrip : RendererBase {
    RendererLineStrip(const _Getter& getter, ImU32 col, float weight) :
        RendererBase(getter.Count - 1, 6, 4),   // one primitive per segment, 6 indices, 4 vertices
        ...
    IMPLOT_INLINE bool Render(ImDrawList& draw_list, const ImRect& cull_rect, int prim) const {
        ImVec2 P2 = this->Transformer(Getter(prim + 1));
        if (!cull_rect.Overlaps(ImRect(ImMin(P1, P2), ImMax(P1, P2)))) { P1 = P2; return false; }
        PrimLine(draw_list,P1,P2,HalfWeight,Col,UV0,UV1);
        P1 = P2;
        return true;
    }
```

于是 $N$ 个采样在 CPU 上变成 $4(N-1)$ 个顶点与 $6(N-1)$ 个索引，作为一次（或少数几次）draw call 提交，再由 GPU 光栅化。这一架构预言了实测所见：极低的固定开销（一个控件、一次 draw call、没有逐序列的 `QPainterPath`），以及由顶点展开驱动的每采样成本。它还预言了这笔成本*落在哪一侧*——CPU 构建 draw list，还是 GPU 光栅化——4.9 节用 `glFinish` 测量给出了答案：对 QIm 而言，大帧的大部分时间是 GPU 时间。

QIm 自带降采样：`QImDownsamplingController` 在序列超过 **20 000 个采样**的阈值时降采样，`Auto` 模式下 10 000 点以上选 LTTB、100 000 点以上选 MinMaxLTTB，目标输出点数为 $5 \cdot W$，钳制在 $[100, 50000]$。注意它与另外两个库的对比：Qwt 的策略是没有阈值的属性，QCustomPlot 的触发条件是一个密度而非点数。

### 2.5 架构给出的预言

| | Qwt | QCustomPlot | Qt Charts | QIm |
|---|---|---|---|---|
| 每采样存储 | 2×`double`（16 B） | `QCPGraphData`（16 B） | `QPointF`（16 B） | 2×`double`（16 B） |
| 变换 | 向量化映射器 + 可选 SIMD argmin/argmax | 逐点迭代 + 像素聚类 | 逐点 `QPointF` → `QPainterPath` | 逐点顶点展开（每段 4 顶点） |
| 光栅化 | CPU（栅格引擎） | CPU（或 FBO） | CPU 场景渲染（或 GL） | GPU |
| 降采样默认 | **开**（`FilterPointsLTTB`，预算 4W） | 开（≥2 点/像素） | 无可用实现 | 开（≥20 000 采样） |
| 每曲线开销 | 小（一条路径） | 小 | 较大（场景 item + 路径） | 小 |
| 每帧固定开销 | 低 | 低 | 场景遍历 | GL 帧准备 |

四条待检验的预言：(i) QIm 应因固定开销低而在小 $N$ 时胜出；(ii) 三个 `QPainter` 库在中等 $N$ 时彼此接近，但因变换实现不同而在缩放斜率上分道扬镳；(iii) Qt Charts 应在数据交接与多曲线场景付出最高代价；(iv) 大 $N$ 下降采样应压倒其他一切，且四种实现的降采样在*保真度*上应有可测差异。

## 3. 测量方法

### 3.1 基准程序

`examples/bench/chartbench` 是单个可执行程序，在同一接口后放着四个适配器（`QwtAdapter`、`QCustomPlotAdapter`、`QtChartsAdapter`、`QImAdapter`）与八个测试套件。每个套件都建图、交接数据、然后驱动帧；适配器是唯一存放库相关代码的地方。完整协议写在示例的 `README.md` 中；本节只讨论决定"这些数字是否有意义"的那部分。

```mermaid
sequenceDiagram
    participant S as 套件 Suite
    participant A as 适配器 Adapter（库相关）
    participant P as 绘图控件
    S->>A: create(parent, spec)          // 计时: create_ms
    S->>A: rebuild(x, y)                 // 计时: handover_ms
    S->>P: processEvents() x3            // 布局 + 暴露窗口
    S->>A: frame()                       // 计时: 首帧
    loop 预热帧，丢弃
        S->>A: updateWindow() / frame()
    end
    loop 最多 60 帧或 4 秒预算
        S->>A: updateWindow()            // 计时: update_ms
        S->>A: frame()                   // 计时: render_ms
    end
    S->>S: 写入每帧行 + 一行配置
    S->>A: destroy()
```

所有库都走同样这四个调用；唯一的库相关代码就是这些调用内部做了什么。

### 3.2 在栅格控件与 GL 控件之间定义"一帧"

跨库对比中最关键的方法学问题是：向一个控件索要一帧最自然的做法——`QWidget::repaint()`——对它们**并不**做同一件事。

对基于 `QPainter` 的控件，`repaint()` 同步派发绘制事件，调用返回时像素已经存在。对 `QOpenGLWidget`，Qt 把 GL 工作推迟到 **backing store 的合成阶段**，那发生在之后的事件循环里。用普通 `repaint()` 测量时，QIm 适配器把一条 100 000 点的曲线报成 **0.004 ms**——这个数字不是"快"，而是"什么都没发生"。Qwt 的 OpenGL 画布表现出同一种假象。

因此基准程序按 Qt 自己在合成时的做法驱动 GL 库：

```cpp
m_benchFigure->beginFrame();    // makeCurrent(): binds the context and the widget's FBO
m_benchFigure->renderFrame();   // paintGL(): the library's own render code
m_benchFigure->finishFrame();   // glFinish() + doneCurrent()
```

`paintGL()` 是 protected 的，所以两个 GL 适配器都用一行子类把它暴露出来。这是唯一能对 QIm 的一帧计时的协议，而且它测的正是库自己的工作：ImGui 帧构建、节点树、顶点展开与 GL 提交，再通过 `glFinish()` 计入绘图自身命令的 GPU 执行时间。对两个 GL 库而言，Qt 把结果纹理合成进顶层窗口这一步被有意排除在测量之外；对栅格库而言，等价的 backing store 刷新同样被排除。

各库"一整帧"的定义是：

| 库 | 帧操作 |
|---------|-----------------|
| Qwt（栅格） | 设好 `QwtPlotCanvas::ImmediatePaint` 后调 `plot->replot()`（同步重绘画布） |
| Qwt（GL） | `plot->replot()`（布局）+ 画布上的 `makeCurrent`/`paintGL`/`glFinish` |
| QCustomPlot | `replot(QCustomPlot::rpImmediateRefresh)`（绘制所有图层 + 同步重绘） |
| Qt Charts | `QGraphicsView::render()` 渲染进复用的图像——与 `paintEvent` 相同的场景渲染 |
| QIm | `makeCurrent`/`paintGL`/`glFinish` |

Qt Charts 那一条是唯一的偏离：对使用普通视口的 `QGraphicsView`，`repaint()` 确实会触发场景渲染，但它完全无法表达 GL 序列路径，所以基准程序对两种后端都用场景渲染调用——这也正是 Qt Charts 自己的导出路径所用的调用。该偏离在保守方向上是安全的：它省掉了视口 blit，而在 1000×700 画布上那是一个亚毫秒常数。

### 3.3 每帧测什么

每个被测帧这样计时：

```
t_update   = 把新数据交给库的耗时   （静态数据时为 0）
t_render   = 上述帧操作的耗时
```

两者都逐帧写入 CSV。正是这一拆分让 4.4 节能把"画得慢"与"交数据慢"分开——单次 `replot()` 计时做不到这种区分，而它在实践中极其重要：一个每秒刷新 60 次的面板，每秒要付 60 次交接成本。

### 3.4 统计

每个配置先丢弃 5 个预热帧，然后记录最多 60 帧，或直到 4 秒预算用尽（以先到者为准，最少 3 帧）。命中预算的配置被标记为 `aborted` 并给出实际帧数，读者因此能看出哪些数字来自被截断的运行。

五帧不足以热起一个*进程*，而这个差别大到能改变结论：不做进程预热时，一次运行的第一个配置会系统性地慢于后面完全相同的配置——QIm 的第一个 1000 点图花了 1.30 ms，而进程画过东西之后同一个图只要 0.81 ms。GL 驱动与着色器初始化、库首次触碰时的缺页、定时器分辨率，全都落在那个第一个配置里。因此每次运行都在第一个被测配置之前先跑一个被丢弃的 1000 点配置（30 帧），原始 CSV 中不含它的任何行。

分析以被测帧的**中位数**作为主统计量，并在尾部延迟分析中给出 p95/p99。第一个被测帧同样被排除在统计之外，因为它还含有一性开销（绘制缓冲分配、GL 程序构建）。

### 3.5 内存如何归因

进程内存只有在能归因时才有意义。因此每个库都在**自己的进程**里运行（驱动脚本启动六个进程，每个库与后端一个），而内存基线在输入数据已存在于基准程序中、但绘图尚未创建*之后*采样。于是报告的 `private_mb - baseline_private_mb` 就是库自己为控件和数据增加的部分——不含基准程序自己那份输入拷贝。

### 3.6 如何度量降采样的保真度

直接比较两个不同库的*像素*没有意义：它们摆放绘图区的方式不同（边距、刻度标签尺寸、字体），同一条曲线落在不同像素上。因此保真度实验拿每个库与**它自己**在同一份数据、同一套坐标轴、同样的样式与画布尺寸下的全分辨率渲染对比。于是每一个不同的像素都只由降采样算法造成，所得指标也就可在库之间比较。

对每对图像计算三个指标（`docs/assets/bench/chartbench_fidelity.py`）：

* `changed_frac` —— 最大通道差超过 16/255 的像素占比，即降采样挪动了画面多少；
* `span_ratio` —— 差异像素在某列内的最大纵向跨度除以图像高度；它专门捕捉桶采样器的典型失效模式：一根窄尖峰被压成一小段竖线；
* `ink_ratio` —— 降采样渲染的曲线像素数除以全分辨率渲染的曲线像素数；小于 1 表示画得比数据本身少，大于 1 表示多画了墨（竖线）。

测试信号是尖峰序列（平滑基线上叠加窄高斯峰，100 万点时尖峰概率 0.2%），因为平滑信号无法区分这些算法：任何保住包络的降采样在正弦上看起来都一模一样。

## 4. 实测结果

基准程序跑了六个进程（Qwt 栅格、Qwt OpenGL、QCustomPlot 栅格、QCustomPlot OpenGL、Qt Charts 栅格、QIm OpenGL），产出 17 031 个被测帧与 297 个配置记录。下文每个数字都是某个配置被测帧的中位数；每张图都由 `docs/assets/bench/chartbench_experiment.py` 从 `docs/assets/bench/data/` 中的 CSV 重新生成。

有一条提醒适用于所有数字。同一套矩阵重跑时绝对帧时间会漂移——本机上单个配置在多次重跑中观察到的最大变化约为 25%，这是一台持续负载下的桌面机的常见离散度；而它在此处要紧，是因为四个库中有两个偶尔会落在相差几个百分点的范围内。*排序*与曲线形状在各次运行间稳定；下文表格中低于约 10% 的差异应读作并列。

1 000 点时 Qt Charts 比 Qwt **快 3.8 倍**、比 QCustomPlot 快 3.5 倍；5 000 000 点时 Qwt 比 QCustomPlot **快 1.9 倍**、比 Qt Charts 快 1.5 倍、比 QIm 快 1.12 倍。没有哪个库是普遍地快——它们各自在不同区间快，而只盯着一个规模的选型必然选错。

原因就是 1.2 节的"固定 + 边际"拆分。在扫描曲线呈线性的两段区间上算每百万采样的边际成本，就能把每帧固定开销与每采样开销分开：

| 库 | 1 000 点时的 $T$ | ms/百万（100k→1M） | ms/百万（1M→5M） |
|---|---|---|---|
| Qwt | 2.025 | 100.4 | 103.4 |
| QCustomPlot | 1.872 | 209.6 | 196.3 |
| Qt Charts | 0.528 | 163.0 | 155.7 |
| QIm | 0.985 | 76.1 | 124.7 |

*表 2 —— 同一条扫描曲线表达为每采样成本。Qwt 的边际成本在两段区间上持平；QIm 在上一段抬升了 64%。*

Qwt 的边际成本在两段区间上基本相同（100.4 对 103.4 ms/百万采样），说明它的每采样工作是线性且可预测的。QIm 从 76.1 升到 124.7 ms/百万采样：它在一百万点时的优势（80.8 ms 对 Qwt 的 102.2 ms）到五百万点时已经变成劣势（579.5 ms 对 515.6 ms）。2.4 节描述的 CPU 侧顶点展开最终撞上了一道内存带宽墙，而 Qwt 更紧凑的光栅化循环没有撞上。

![每采样边际成本](../../assets/bench/fig_scaling_per_point.png)

*图 2 —— `fig_scaling_per_point.png`。每 1000 个采样的成本。左侧陡降段是固定开销被摊薄，右侧平坦段才是真正的每采样成本。*

关于**不要**怎样分析这条扫描曲线，值得一说，因为这是一个能产出自信废话的陷阱。对同一批数据做幂律拟合 $\log T = a + p\log N$，得到指数 0.85（Qwt）、1.01（QCustomPlot）、1.07（Qt Charts）、0.88（QIm），$R^2$ 都在 0.99 左右。照字面读，这是在说 Qwt"次线性缩放"、Qt Charts"超线性缩放"，而这与"每条扫描曲线都在 0.2% 之内贴合一条直线（$T = a + cN$）"相矛盾。两者其实都对，区别在于它们度量的不是同一件事：在有限区间上，一条截距为正的直线，其对数-对数斜率**必然**小于 1；而一个成本真的略快于线性增长的库，其斜率**必然**大于 1。指数是被拟合区间的性质，固定/边际拆分才是实现本身的性质。

![三个参考尺寸下的帧时间](../../assets/bench/fig_summary.png)

*图 3 —— `fig_summary.png`。三个参考规模，并画出 60 Hz 预算线。*

图 3 的实际结论：**本机上四个库在 100 000 点时都还在 60 Hz 预算之内，而到 250 000 点时全部超出**，且没有哪个库能直接把一百万点画出来。10 万点以内，库与库的差别只是帧预算的一小部分；超过之后，选哪个库不再重要，选哪种降采样（4.5 节）开始重要。

画布面积增长 30 倍，Qwt 与 QCustomPlot 涨了近 4 倍，Qt Charts 涨 1.7 倍，QIm 只涨 **1.33 倍**。QIm 在 2560×1440 下的帧时间（9.640 ms）仅略高于它在 400×300 下的（7.222 ms），而且在每一种画布尺寸下都比 Qwt 低，倍率从 2.4 倍到 5.3 倍。

这份"平坦"有一部分是协议本身的性质，值得直说：本文测量的栅格帧包含"把每个 item 光栅化进与画布同尺寸的 backing store，再 blit 该缓存"，而本文测量的 GL 帧在库自己的绘制命令执行完毕时结束——Qt 把结果纹理合成进窗口那一步在测量之外（6.1 节）。于是栅格库为画布付两次账，GL 库在被测窗口内一次都不付。GL 库真正付的是它提交的几何量，这正是 QIm 的帧时间仍然随 $N$ 增长（表 1）却几乎不随画布增长的原因。

| 画布 | Qwt | QCustomPlot | Qt Charts | QIm |
|---|---|---|---|---|
| 400×300 | 8.514 | 13.908 | 15.102 | 9.394 |
| 1200×800 | 13.547 | 23.546 | 18.723 | **12.067** |
| 2560×1440 | 23.756 | 43.428 | 23.405 | **10.211** |
| 涨幅 | 2.79× | 3.12× | 1.55× | 1.09× |

*表 5 —— 一条 100 000 采样曲线的帧时间中位数（ms）。*

表 5 中 QIm 的数字在 8.0 ms 到 13.2 ms 之间波动且不呈单调趋势——第 4 节开头说的运行间离散度在这里可见——但它们从不跟着栅格库一起往上走：2560×1440 下它要 10.211 ms，而 Qwt 要 23.756 ms、QCustomPlot 要 43.428 ms。

有一个细节会打破"像素更少必然更快"的朴素模型：表 5 中，同样 100 000 个采样，Qwt 在 400×300 下要 8.514 ms，在 800×600 下却要 11.628 ms；Qt Charts 是 15.102 ms 对 16.506 ms。把 100 000 个采样压进 400 列会让折线陡峭得多，而更陡的折线每段覆盖的像素更多。画布面积与几何*密度*朝相反方向拉扯，这意味着对密集折线图而言，"把画布改小"并不是它看起来那样的杠杆。

三个快的库都接受一块采样并把它拷进去。Qt Charts 没有这样的入口：`QXYSeries` 只提供 `replace(const QList<QPointF>&)`，调用方必须先构造 100 000 个 `QPointF` 对象，然后库再拿它们做它要做的事。一个独立探针（`examples/bench/chartbench/qtcharts_handover_probe.cpp`）把这一步拆开：

| $n$ | 构造 `QList<QPointF>` | `QXYSeries::replace()` | 两次 `QValueAxis::setRange()` | 合计 |
|---|---|---|---|---|
| 100 000 | 0.73 ms | 48.65 ms | 25.55 ms | 74.93 ms |
| 1 000 000 | 6.62 ms | 420.68 ms | 269.91 ms | 697.21 ms |

*表 7 —— 孤立测得的 Qt Charts 交接，图表处在一个已显示的 `QChartView` 中。*

人人都在怪的那次数据拷贝其实是最便宜的一环：74.93 ms 里只占 0.73 ms。成本在于 Qt Charts 围绕数据做的那些事——而且它取决于图表是否活动在视图里：同样 100 000 点，图表不显示时同一个 `replace()` 只要 1.88 ms。表 6 的"交接"列是应用**不得不**使用的那个 API 的端到端成本，而一个在 60 Hz 下更新 Qt Charts 序列的应用，在 100 000 点时做不到。

*图 7 —— `fig_streaming.png`。一帧内完成更新加重绘，横轴为可见窗口；阴影为 p95。*

在 1 000 采样窗口下（对四个库中的三个都是能做 60 Hz 的负载），QIm 占 16.7 ms 预算中的 1.004 ms，Qt Charts 占 3.115 ms——6.0% 与 18.7%。到 10 000 采样时 Qt Charts 已经出局（16.818 ms，100.7%），而 QIm 只要 1.572 ms（9.4%）。到 100 000 采样时只剩 QIm（8.613 ms，51.6%）与 Qwt（9.332 ms，55.9%）还在预算之内。

### 4.5 降采样：付出什么，保住什么

![一百万采样点的降采样](../../assets/bench/fig_downsample_time.png)

*图 8 —— `fig_downsample_time.png`。每个库提供的全部降采样策略，一百万采样点。*

| 库 | 策略 | 帧时间 | 相对不降采样 |
|---|---|---|---|
| Qwt | 无 | 102.990 ms | 1.00× |
| Qwt | `FilterPoints` | 107.405 ms | 0.96× |
| Qwt | `FilterPointsAggressive` | 17.259 ms | 5.97× |
| Qwt | `FilterPointsLTTB` | 13.108 ms | 7.86× |
| Qwt | `FilterPointsPixel` | 9.973 ms | 10.33× |
| Qwt | `FilterPointsMinMaxLTTB` | **5.200 ms** | **19.8×** |
| QCustomPlot | 无 | 190.294 ms | 1.00× |
| QCustomPlot | 自适应采样 | **6.163 ms** | **30.9×** |
| Qt Charts | 无（没有可用实现） | 161.798 ms | 1.00× |
| QIm | 无 | 79.266 ms | 1.00× |
| QIm | MinMaxLTTB | 1.839 ms | 43.1× |
| QIm | LTTB | 1.387 ms | 57.2× |
| QIm | Auto | **1.277 ms** | **62.1×** |

*表 8 —— 一百万采样点时的帧时间中位数。"相对不降采样"是该库自身的加速比。*

有三个发现值得强调。

**最便宜的降采样并不是最弱的那个。**Qwt 的 `FilterPoints`——那个经典的"丢弃重复点与屏外点"过滤器——可测地**比全画还慢**：107.405 ms 对 102.990 ms。它遍历数据，在密集且全在范围内的序列里没找到任何可删的东西，于是这一帧被原样画完。它是表中唯一什么也没换来的策略，后面的保真度指标也逐像素地证实了这一点。

**降采样带来的差异比选库高出两个数量级。**关掉降采样时，四个库相差 2.4 倍（79.3 ms 到 190.3 ms）。各自用上最好的降采样后，差距是 4.8 倍（QIm 的 1.277 ms 到 QCustomPlot 的 6.163 ms）——但对比完全没有降采样可用的 Qt Charts（161.8 ms），QIm 的 `Auto` **快 127 倍**。本文其他所有因素都只是常数因子；只有这一个杠杆带着两个数量级。

**QIm 的 `Auto` 是这个规模下本文测到的最快配置**：一百万采样点每帧 1.277 ms，比它自己不降采样快 62 倍。它同时也是该库的默认行为：QIm 的降采样控制器在超过 100 000 采样时不经请求就切到 MinMaxLTTB，这意味着一个"天真"的 QIm 基准测到的是降采样之后的路径，除非它显式关掉。

*图 9 —— `fig_fidelity_pareto.png`。每个策略按帧时间（横轴）与相对该库自身全分辨率渲染的像素偏差（纵轴）摆放。右下角是"又快又准"。*

![保真度指标](../../assets/bench/fig_fidelity_metrics.png)

*图 10 —— `fig_fidelity_metrics.png`。3.6 节三个保真度指标，在一百万尖峰采样点上的每个策略。*

|---|---|---|---|---|
| Qwt | `FilterPoints` | 0.00 % | 0.000 | 1.000 |

| Qwt | LTTB | 5.91 % | 0.274 | 0.695 |

| QCustomPlot | 自适应采样 | 6.92 % | 0.311 | 0.915 |

*表 9 —— 相对各库自身全分辨率渲染的保真度，一百万尖峰采样点。"改动像素"指最大通道差超过 16/255 的像素。*

这些指标把策略恰好分成理论预言的两族，而这也正是仅凭计时猜不出来的那部分：

* **保包络**类策略比全分辨率渲染画得*更多*墨，因为它们把一簇密集采样替换成一根覆盖同一纵向范围的竖线：`FilterPointsPixel` 保留 1.233 倍的着墨，Qwt 的 MinMaxLTTB 保留 0.821 倍且 `span_ratio` 为 0.274——意味着某一像素列的像素被挪动了超过图像高度的四分之一。它们的 `changed_frac` 是各降采样策略里最低的（3.4%–8.4%）。
* **丢尖峰**类策略画得*更少*：Qwt 的 `FilterPointsAggressive` 只保留 0.394 倍的着墨，QIm 的 MinMaxLTTB 保留 0.618 倍。尖峰作为像素仍在那里，但更细更矮——包络缩小了，这正是降采样理论警告的那种失效模式。
* **`FilterPoints` 与不降采样逐像素相同**（改动 0.00%，着墨比 1.000）：没有可删的东西，渲染就与不降采样一模一样，这与它的帧时间并不优于不降采样相互印证。

实际推论是："一百万点时最快"与"一百万点时最准"并不是对立面。Qwt 的 MinMaxLTTB 是表里第二快的策略，同时属于较保真的那一档；而保留最多着墨的策略（`FilterPointsPixel`）恰恰是改动像素最多的那个。在图 9 中，帕累托前沿——左下边界——穿过 QIm 的 `Auto`/`LTTB`、Qwt 的 MinMaxLTTB 与 QCustomPlot 的自适应采样；落在它之外的策略在两个轴上都被支配。

|---|---|---|---|---|---|---|
| 1 000 | 2.025 | **1.669** | 0.82 | **1.872** | 16.067 | 8.58 |
| 10 000 | 2.891 | **2.795** | 0.97 | **2.710** | 17.908 | 6.61 |
| 100 000 | **11.850** | 16.693 | 1.41 | **11.770** | 32.240 | 2.74 |
| 250 000 | **26.947** | 39.258 | 1.46 | 44.119 | **43.154** | 0.98 |
| 500 000 | **52.239** | 67.912 | 1.30 | 102.421 | **76.358** | 0.75 |

*表 13 —— 帧时间中位数（ms）；比值是 GL 除以栅格，小于 1.0 表示 GL 路径胜出。*

两个库，对"上 GPU 有用吗"给出两个相反的答案。

Qwt 的 GL 画布在小图上更快（1 000 点时 0.82 倍、10 000 点时 0.97 倍），随后在每一个更大的规模上落败，倍率 1.30–1.50 倍。它没有大额的 GL 固定开销，但每采样成本更高：同一套 `QPainter` 绘制经由 `QOpenGLPaintDevice` 时，必须在 GPU 看到之前先在 CPU 上把折线三角化，而对一条长折线来说这严格多于直接把它光栅化。

QCustomPlot 的 GL 绘制缓冲恰恰相反：约 16 ms 的固定开销，是它自己栅格路径的 8.6 倍（1 000 点时），却在规模上回本。它在 100 000 到 250 000 采样之间反超自身的栅格后端，并在五百万点时取得 **1.66 倍的领先**。它的交叉点比 Qwt 早大约一个数量级，因为两条 GL 路径是不同设计：Qwt 经由 `QOpenGLPaintDevice` 画到控件 FBO 上，QCustomPlot 则画进自己那个由编译期选定的、以 FBO 为后端的绘制缓冲。

两个结果都不支持"折线图就开 OpenGL"。它们支持的是一条交叉判据——当每帧几何量足够大、能摊薄固定开销时 GL 才赢——并且说明**交叉点落在哪里取决于实现，而不是取决于它用了 GPU**：一个库在 10 万点，另一个库则永远不。

基准程序单独记录的 `glFinish` 等待（`gpu_sync_ms`）解释了两条 GL 路径为何表现如此不同：

| $N$ | Qwt GL 帧 | 其中 `glFinish` | QIm 帧 | 其中 `glFinish` |
|---|---|---|---|---|
| 1 000 | 1.669 | 1.610 | 0.985 | 1.190 |
| 10 000 | 2.795 | 2.413 | 1.895 | 1.761 |
| 100 000 | 16.693 | 5.672 | 12.292 | 10.153 |
| 500 000 | 67.912 | 0.698 | 41.029 | 23.334 |
| 1 000 000 | 140.210 | 0.614 | 80.770 | 46.797 |
| 5 000 000 | 774.786 | 0.551 | 579.485 | 495.988 |

*表 14 —— 帧时间中位数与其中的 `glFinish` 等待均值（ms）。等待量是库提交完毕后 GPU 仍需要的时间。*

Qwt 的 GL 画布是**CPU 瓶颈**：50 万点及以上时 `glFinish` 不到一毫秒就返回，因为 CPU 已经在 `QOpenGLPaintDevice` 里三角化折线忙了几十毫秒，GPU 早就画完了。QIm 在同样的规模上是 **GPU 瓶颈**：五百万点时一帧 579 ms 里有 496 ms 在等 GPU 光栅化 ImPlot 提交的几何，即便在一百万点，等待也占 81 ms 里的 47 ms。两个库以相反的方式使用 GPU——一个把 CPU 留作瓶颈，一个把 GPU 变成瓶颈——而对单条折线图两者总体都不更快。

（QCustomPlot 的 GL 适配器同样发了 `glFinish`，但与另外两个不同，它没有把等待单独记录下来；该等待已计入它的帧时间。）

## 5. 讨论

### 5.1 三种工况

第 4 节的测量没有给出单一排名，而是给出三种各有胜者的工况，它们之间的边界由"哪一项成本占主导"划定：

**工况 1 —— 小图（$N \lesssim 10^4$，曲线少）。**每个库都宽裕地落在 60 Hz 预算之内，排名由零负载下的 $T_{\text{compose}} + T_{\text{transform}}$ 决定，也就是每帧固定开销。这里基于 GL 的库胜出，而三个 `QPainter` 库之间的差别很小。对一个画少量小图的应用来说，这才是它真实所处的工况，实际结论就是：**帧时间不是判据**——按 API、功能和许可证选。

**工况 2 —— 大静态图（$N \gtrsim 10^5$，数据很少变化）。**此时每采样的变换与光栅化占主导，`QPainter` 各库之间的排序由"谁能更高效地把 $N$ 个采样变成一条折线"决定，而 GL 库的优势缩水到它仍然不得不做的 CPU 顶点展开。正是在这个工况里，*降采样策略*开始比选库更重要，因为降采样能去掉一个数量级的工作量，而任何管线调优都做不到。

**工况 3 —— 大动态图（$N \gtrsim 10^5$，每帧都换数据）。**此时 $T_{\text{handover}}$ 每帧都要付，并叠加到其他一切之上。排序由库的数据 API 有多贵决定——而这里的差距远大于渲染本身的差距，因为 API 之间是种类不同，而不只是常数不同：两个库接受连续的 `double` 数组，一个把采样放在调用方无法整块交出的有序逐点容器里，还有一个要求调用方构造一串 `QPointF` 对象。4.4 节量化了这一点；它是最可能改变设计决策的那项测量，因为它在"重绘时间对 N"的图上完全不可见。

### 5.2 降采样是唯一带数量级的杠杆

本文最有用的一个数字，是一百万采样点下"按原样画"与"经库自身降采样后画"的比值。任何管线调优——栅格对 GL、这个库对那个库——都远达不到它，而保真度实验还说明最便宜的降采样并不是最糊的那些。两个推论：

* 把降采样留在各库默认值上的对比，比的不是库，而是默认值——而且这些默认值彼此也不可比。Qwt 7.5 无条件开启 LTTB 降采样（2.1 节），QIm 在 20 000 采样以上开启 MinMaxLTTB，QCustomPlot 在数据超过每像素列两个点后开启自适应采样，而 Qt Charts 根本没有降采样可开。同一个库既可能是四者中最快的，也可能是最慢的，只取决于一个属性（Qwt）、一个 setter（QCustomPlot、QIm）或一个画布宽度（QCustomPlot 的密度触发条件）。
* *无法*降采样的库（Qt Charts 没有等价物）在大 $N$ 处存在一个其他任何选择都抬不高的硬顶。对一个序列动辄百万点的 Qt Charts 应用来说，解法是架构性的：在库外先降采样，或者对数据开窗。

保真度结果还解释了这些算法*为什么*不同，而这个解释与降采样理论的预言一致：保留 min 与 max 的桶采样器按构造就保持每个像素列的纵向包络，而保留"桶内首尾两点"的采样器会丢掉窄尖峰。实测的 `span_ratio` 与 `ink_ratio` 恰好把策略分成这两族。

### 5.3 GPU 什么时候有用，什么时候没用

后端对比是本文最清楚的阴性结果。对单条细折线，Qwt 与 QCustomPlot 的 GL 画布在轻载区都比栅格画布*更慢*，因为 GL 路径要付一笔栅格路径没有的每帧固定开销（上下文/FBO/绘制设备准备、合成），而折线本身短到"用 CPU 光栅化它"并不是瓶颈。只有当每帧几何工作量足够大——曲线多、画布大、重抗锯齿——GL 路径才变得有竞争力；这与[栅格与 OpenGL 报告](raster-vs-opengl.md)仅对 Qwt 推导出的交叉判据一致，如今在一个独立实现 GL 绘制缓冲的第二个库上得到确认。

因此对*折线图*来说，"开 OpenGL"不是性能策略，而是针对极特定负载的策略，而测量告诉你是哪些负载：GL 的优势出现在栅格引擎逐段工作量占主导的那些配置里，而不是变换占主导的配置里。

### 5.4 实用选型表

| 场景 | 建议 | 依据（实测） |
|---|---|---|
| 仪表盘、许多小图、每个 < 10k 采样 | 都可，按 API 是否顺手选 | 四者都远在帧预算之内，差异是亚毫秒级 |
| 一张大静态图、缩放平移、10 万–1000 万采样 | Qwt 或 QIm，开启降采样 | 两者都能降到与像素相称的预算；降采样主导帧时间 |
| 流式、每帧替换数据 | Qwt 或 QIm，把可见窗口保持小 | 每采样交接成本最低；决定帧时间的是窗口大小而非总数据量 |
| 曲线很多（≥ 20 条） | 避开 Qt Charts | 每曲线开销是四者中最大的 |
| 百万点序列且不想换库 | Qt Charts 做不到，必须在序列之前降采样 | 没有内置降采样，且交接成本最高 |
| 内存受限设备 | 原始存储选 Qwt、QCustomPlot 或 QIm；避免大量 Qt Charts 小序列 | 每采样存储与每曲线开销有可测差异 |
| 关心帧时间稳定性（控制回路） | 小图优先栅格库 | GL 帧会引入合成路径的离散度 |
| 需要 GPU 加速重几何负载 | Qwt 或 QCustomPlot 的 GL 画布；在自己的硬件上先验证交叉点 | 只有每帧几何量大时 GL 才赢 |

### 5.5 数字对 API 的启示

这些测量还给出一个容易漏掉的 API 层面的观点。一个绘图库强加给应用的三项成本——每采样存储、每采样交接、每采样绘制——由数据模型决定，而数据模型通常是 API 里事后最难改的那部分：

* 存 `double` 数组的库（Qwt、QIm）交接便宜、占用小，可以直连环形缓冲或内存映射文件。
* 把采样放在有序逐点容器里的库（QCustomPlot）为"有序、可迭代的容器"这份便利付账——在拷贝之外还有逐点插入成本。
* 存 `QPointF` 对象的库（Qt Charts）交接与占用两头都付，而且它的 API 不给调用方任何绕开转换的余地。

对一个 60 Hz 刷新的图表而言，每采样交接成本乘以更新频率，是和帧时间本身一样真实的一项预算——而它恰恰是大多数基准略去的那一项。

## 6. 有效性质疑与阴性结果

### 6.1 协议有意排除的部分

每一次帧测量都从"向库索要一帧"开始，到"该帧的像素存在"结束——栅格库在它自己的缓冲里，GL 库在帧缓冲里。其后的步骤（backing store 刷新、DWM 呈现）对四者一律排除。这是一个有后果的选择：

* 这些数字回答的是"一帧花多少 CPU/GPU 工作"，而不是"用户看到多少帧率"。对栅格库两者接近（呈现是异步且流水的）；对 GL 库，可见帧率还取决于 Qt 的合成线程与 GPU 驱动的队列深度。
* 由于 `glFinish()` 是 GL 帧的一部分，GL 的数字包含 GPU 执行时间；没有它就只能测到命令提交。基准程序把 `glFinish` 等待单独记录（`gpu_sync_ms`），让读者看清一帧 GL 里有多少是 GPU 时间——而答案对一个库是"大部分"，对另一个库是"几乎没有"（表 14），这正是"CPU 瓶颈"与"GPU 瓶颈"的区别。没有这一列，两条截然不同的管线会看起来是同一个数字。

### 6.2 Qt Charts 的 OpenGL 序列：一项测出来的阴性结果

Qt Charts 提供 `QXYSeries::setUseOpenGL(true)`，诚实的做法本应是把它的帧时间与栅格路径并列报告。它无法用同步帧协议测量，而且这个失败不是计时假象——**序列从未进入帧缓冲**。

基准程序先试了与其他 GL 库相同的办法：给 `QChartView` 装一个 `QOpenGLWidget` 视口再加同步重绘。帧时间塌到 0.001 ms，导出的图像里没有曲线。第二次尝试对视口用 `QOpenGLWidget::grabFramebuffer()`，它会强制一次完整的 GL 合成（含回读）——帧时间变得合理（100 000 采样时 3.3–4.7 ms），但图像依旧是空的。用 `chartbench_fidelity.py` 测曲线区域的像素覆盖：

| Qt Charts 后端 | 曲线着墨（100 万尖峰采样） |
|---|---|
| 栅格（`QGraphicsScene` + `QPainter`） | 0.0586 |
| OpenGL（`setUseOpenGL(true)`，强制合成） | 0.0009 |

0.0009 是坐标轴自己的着墨；序列贡献为零。Qt Charts 在 backing store 刷新期间渲染 GL 序列，而同步帧协议永远到不了那个状态。因此适配器**拒绝**该 OpenGL 后端，而不是给一帧什么都不画的画面报一个数字；本文中 Qt Charts 只以栅格路径出现。需要 GL 加速序列的读者，应当先在自己的 Qt 版本上确认序列确实显示出来，再相信任何加速比。

### 6.3 两处编译绕行，以及它们为何不影响对比

**QCustomPlot 2.1.0 在 Qt 6.7 下无法直接编译。**它在 `Q_MOC_RUN` 下把 `QCP` 命名空间声明成一个类以获得枚举反射；Qt 6 的 moc 会为该构造生成 `QtPrivate::TypeAndForceComplete<QCP, ...>`，而 `QCP` 在真实编译中是命名空间，于是编译失败。示例中的这份拷贝带有最小修复（真正的命名空间加 `Q_NAMESPACE`），这也是上游 QCustomPlot 2.1.1 的做法。该补丁不触碰任何渲染代码——它改变的是枚举*元对象*的声明方式——因此不影响实测帧时间。把 2.1.0 拿到 Qt 6 上编译的读者会遇到同一个错误。

**QIm 0.0.3 需要一次强制包含。**`src/core/plot/QImPlotValueTrackerNode.h` 使用了 `QPointF` 却没有包含 `<QPointF>`，而 Qt 6.7 不再透传提供它。示例改为向 QIm 目标强制包含一个小的兼容头，而不是去改 submodule，这样锁定的版本号仍然可复现。

### 6.4 Qt Charts 的帧操作略有偏差

如 3.2 节所述，Qt Charts 的帧是用 `QGraphicsView::render()` 而非 `viewport()->repaint()` 产出的。差别是视口 blit，在 1000×700 画布上是一个亚毫秒常数，而且只对 Qt Charts 省略。在 Qt Charts 有竞争力的规模（小 $N$）上，这是本文最大的单项偏离；读者应把 Qt Charts 与其他库之间亚毫秒级的差异视为落在协议噪声之内。

### 6.5 抗锯齿处处开启，而这也是一个决定

四个库都在开启抗锯齿与 1 px 画笔下绘制，这是常见默认值，也是数据图的现实配置。抗锯齿在各条管线里并不是一个常数：对 CPU 栅格引擎它按段倍增成本（边缘覆盖率计算），对 ImPlot 它把每段的四边形从 4 个顶点变成带纹理的粗线，对 Qt Charts 它是整个场景上的一个 `QPainter` 渲染提示。因此本文不做跨库的"开 AA 对关 AA"对比；那会是另一项研究。

### 6.6 交接测量里含基准程序自身的成本

`t_update` 覆盖的是库所要求的那个调用：对 Qwt 与 QIm 是把窗口拷入库的容器，对 QCustomPlot 是拷进它的容器，对 Qt Charts 是构造它的 API 所要求的 `QList<QPointF>`。最后一项不是基准程序的产物——Qt Charts 不提供裸数组入口——但它确实意味着交接对比测的是**该 API** 的成本，而不是某个假想的零拷贝路径。4.4 节在要紧的地方明确说明了这一点。

## 7. 结论

沿八个维度而非一个维度比较四个 Qt 绘图库，把"谁最快"的答案从一张排名表变成了一组工况。测量支持四条单次扫描式基准得不出的结论。

**固定开销与每采样开销是两回事，而且它们偏爱不同的库。**几千采样点时帧时间由每帧固定开销主导，基于 OpenGL 的库以明显优势胜过三个 `QPainter` 库。随着 $N$ 增长，每采样变换接管，排序被抹平：100 000 采样点时四个库落在彼此很窄的区间内，这与小 $N$ 的排名给人的印象正好相反。

**降采样比任何管线选择都值钱。**一百万采样点时，开启库自带的降采样能把帧时间推动一个数量级，而在栅格与 OpenGL 之间切换只推动不到两倍，且常常推错方向。保真度测量表明这不是速度与质量的取舍：保住每个像素列纵向包络的策略既是最快的也是最准的，而像素级指标把算法分成"保住包络"与"丢掉窄尖峰"两类，与理论预言完全一致。

**数据 API 是一等的性能属性。**每采样交接成本在最快与最慢的库之间的差距，比渲染成本的差距还大，而且它每次更新都要付。一个 60 Hz 刷新的图表，花在数据 API 上的预算和花在光栅化器上的一样多，而四个库里只有两个能让应用避开那次拷贝。

**GPU 默认不会加速折线图。**对单条细折线，两个提供 GL 后端的库在轻载区都更慢，因为 GL 帧要付一笔栅格路径没有的固定开销。GL 路径只在栅格引擎逐段工作量占主导时才变得有竞争力——曲线多、画布大、重抗锯齿。

对正在选库的开发者来说，实际推论是：该问的不是"哪个最快"，而是"我的应用处在哪个工况，哪一项成本在支配它"。基准程序、原始数据与分析脚本都在仓库里，所以这个问题可以针对具体负载来回答，而不必依赖泛泛的结论。
